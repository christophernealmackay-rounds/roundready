## Phase 1 — Planning & Architecture

**Goal:** Lock in every architectural decision, document the full system design, and stand up the skeleton project structure before writing any feature code.

### 1.1 Tech Stack Decisions

| Layer | Choice | Rationale |
|---|---|---|
| Frontend framework | Next.js 15 (App Router, client-rendered) | Modern React, fast routing, strong ecosystem |
| Frontend language | TypeScript | End-to-end type safety |
| Styling | Tailwind CSS v4 + CSS variables | Design tokens, utility-first |
| Component library | shadcn/ui | Accessible, composable, unstyled base |
| State management | Zustand | Simple, no boilerplate |
| Charts | Recharts | Composable, React-native charts |
| Drag & Drop | dnd-kit | Modern, accessible |
| Forms | React Hook Form + Zod | Validation and form state |
| Date picker | react-day-picker | Flexible, used by shadcn/ui |
| Icons | Lucide React | Clean, consistent |
| Fonts | next/font — Fraunces, Inter Tight, JetBrains Mono | Per design spec |
| Backend language | Python 3.12 | Modern, typed, strong data/API ecosystem |
| Backend framework | FastAPI | Async, OpenAPI auto-docs, Pydantic validation |
| Database | Supabase (PostgreSQL) | Hosted Postgres, auth, row-level security, real-time |
| ORM | SQLAlchemy 2.x (async) + Alembic | Migrations, type-safe queries |
| Authentication | Supabase Auth (JWT) | Built-in, integrates with RLS |
| Containerization | Docker + Docker Compose | Reproducible local dev and deployment |
| Reverse proxy | Nginx (in Docker Compose) | Route `/api` to FastAPI, `/` to Next.js |
| Testing — frontend | Vitest + React Testing Library | Fast, Jest-compatible |
| Testing — backend | pytest + httpx (async) | FastAPI test client |
| API contract | OpenAPI 3.1 (auto-generated by FastAPI) | Frontend can generate typed client |
| API client (FE) | openapi-fetch (generated) | Type-safe fetch from OpenAPI spec |

### 1.3 Database Schema Design

Core tables (full column definitions in `docs/schema.sql`):

| Table | Key Columns |
|---|---|
| `users` | id, name, email, role, department_id, notification_prefs, active |
| `departments` | id, name, facility_id, custom |
| `angels` | id, user_id, department_id, absent, absent_since |
| `residents` | id, name, room_number, bed, angel_id, status, pcc_id |
| `qapis` | id, title, status (active/archived), created_at |
| `qapi_items` | id, qapi_id, title, order |
| `questions` | id, text, section, issue_on (yes/no/either), notify_department_id, repository |
| `round_templates` | id, type (angel/rapid), active, start_date, end_date, archived_at |
| `template_questions` | id, template_id, question_id, qapi_item_id (nullable), order |
| `rounds` | id, template_id, angel_id, completed_at |
| `round_answers` | id, round_id, question_id, answer (bool), issue_flagged |
| `qaa_notes` | id, facility_id, content, updated_at |

Row-level security policies defined per table. Alembic manages all migrations.

### 3.2 Cross-Tab Data Flow Requirements

| Trigger | Effect |
|---|---|
| User deactivated | Linked angel marked absent; residents unassigned |
| Angel marked absent | Residents show "Unassigned" in Residents tab |
| Resident assigned to angel | Angel's count updates; resident no longer unassigned |
| QAPI item created | Appears as linkable target in Rounds builder |
| Question linked to QAPI item | QAPI tab shows linked questions |
| Round completed (simulated) | Dashboard KPI cards update; data available in Reports |
| RapidRound stop date reached | Auto-archived |
| QAPI archived | Removed from Dashboard KPI cards |

## Phase 4 — Backend Development

**Goal:** Build the complete FastAPI backend with all business logic, database models, and seed data. No frontend connection yet — verified via FastAPI auto-docs and pytest.

### 4.1 Build Order

1. **Database layer** — SQLAlchemy async engine, session dependency, Alembic migrations for full schema
2. **Models** — all SQLAlchemy ORM models matching schema from Phase 1
3. **Schemas** — Pydantic v2 request/response schemas for every entity
4. **Auth** — Supabase JWT verification middleware, user context injection
5. **Seed script** — populate all tables with realistic SNF demo data (≥10 residents, ≥4 angels, ≥3 QAPIs, ≥20 questions, ≥30 completed rounds with answers)
6. **Route handlers** — implement all `/api/v1/*` endpoints
7. **Business logic services** — auto-assign, absence handling, redistribution, issue flagging, report aggregation
8. **PCC mock** — `/api/v1/residents/sync` returns static PCC-shaped data

### 4.2 Business Logic Requirements

| Logic | Rules |
|---|---|
| Auto-assign residents | Sequential by room; all beds in same room (101a/b/c) go to same angel |
| Angel absence | Sets `absent=true`; all linked residents get `angel_id=null` |
| Redistribution | Temp-assigns unassigned residents to available angels; stores original `angel_id` for restoration |
| Issue flagging | On round answer submission: if answer matches `issue_on` setting, create issue record and notify department |
| Report aggregation | Group by QAPI, QAPI item, question; calculate % yes/no, issue count, completion rate per angel; filterable by date range, resident, QAPI |
| RapidRound auto-stop | On each round retrieval, check `end_date`; auto-archive if past |

### 4.3 Backend Tests

- [ ] Integration tests for all API endpoints (against test Supabase branch or SQLite in-memory)
- [ ] Auth middleware test (valid JWT passes, invalid rejects)
- [ ] Seed script idempotent (run twice, no duplicates)

### Deliverables
